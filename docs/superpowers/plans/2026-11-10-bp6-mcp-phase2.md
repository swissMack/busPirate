# BP6 MCP server, phase 2 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Recipes that erase, write and verify serial memories (I2C EEPROM/FRAM, SPI flash, SPI EEPROM/FRAM, Microwire 93Cxx, 1-Wire EEPROM), each behind its own yes after a backup, plus read-only DDR4/DDR5 SPD and MIDI recipes.

**Architecture:** A destructive recipe runs in two steps. The power yes (`recipe_run`) applies power, checks the chip and *prepares*: it reads the range it will change, saves a backup, and returns a second token naming exactly what will change. The change yes (`recipe_commit`) re-checks power and the chip, re-reads the range, refuses if anything moved, then writes and verifies. All memory recipes share one write helper (`buspirate/mcp_bp6/memory.py`); chip drivers live in `buspirate/devices/`, and fakes for each chip live in `buspirate/simulator_bp6.py`.

**Tech Stack:** Python (core 3.8-clean), `mcp` SDK (server module only), pytest, `FakeBp6`.

**Spec:** `docs/superpowers/specs/2026-11-10-bp6-mcp-server-design.md` — §4.2 (confirmation rule, destructive second token), §5 (safety per risk), §6 item 2. Research: `docs/superpowers/research/2026-11-10-bp6-use-cases.md` entries B1.1–B1.3, B1.10, B1.11, B2.2–B2.4, B3.2, B4.5.

## Global Constraints

- Everything outside `buspirate/mcp_bp6/server.py` stays Python 3.8-clean (no `match`, no `X | Y` types, no `mcp`/`anyio` imports).
- Tests: `.venv/bin/python -m pytest tests/ -q` (3.9; server tests skip) and `uv run -q --isolated --python 3.13 --with-editable '.[dev,mcp]' python -m pytest tests/ -q`. Never a plain `uv run`.
- The universal `buspirate` server's behaviour and tool list do not change. Its tests keep passing unchanged.
- Power is never switched on without a redeemed power token. `recipe_commit` never switches power on, never changes the voltage, never touches pull-ups.
- A destructive change never runs on the power yes. It needs a commit token: single use, 300 s, tied to the board's port, issued only by a prepare that read the range it will change.
- A backup is saved before every change unless the owner passed `backup=False`. The range is read either way (the commit compares it).
- Every recipe stays at or below 5000 mV (owner's cap). No DDR SPD writes, no write-protection changes (25xx BP bits, 1-Wire protection registers, DDR lock bits): out of scope.
- Hardware facts this plan could not verify are marked `# UNVERIFIED on hardware` in code and listed in `notes/bp6.md`: SPI `chip_select_idle` (Microwire), Microwire read alignment, DDR4 page select, DS2431 copy without strong pull-up.
- Commit after every task with a `bp6-mcp:` prefix, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Branch: `bp6-phase2` (already created from `main`).
- Backup tests redirect `HOME` with `monkeypatch.setenv("HOME", str(tmp_path))`, as phase 1 does.

## Review Focus

1. **Data that does not fit or a missing file** (offset + length past the chip, empty or missing file, both `file` and `data_hex`): refused by the check, before any read or backup, and no commit token. Test in Task 2.
2. **A flash write that does not start or end on a 4 KB sector:** the bytes outside the range, inside the touched sectors, survive. Test in Task 4.
3. **Power gone, or another board, between the two yeses** (`hiz`, a trip, a reconnect): `recipe_commit` refuses and switches nothing on. Test in Task 1.
4. **The chip changed between backup and yes** (swapped, or an older commit token used after a newer one already wrote): the re-read differs, so the commit refuses. Test in Task 2.
5. **A write-protected chip ignores the write:** the commit reports `verified: False`, the first bad offset and the backup path, and says to check WP. It never reports success. Test in Task 2 (a fake whose writes are ignored), and per chip where the fake supports protection (Tasks 3, 4).

### Task 2: The shared memory-write helper

**Files:**
- Create: `buspirate/mcp_bp6/memory.py`
- Test: `tests/test_mcp_bp6_memory.py`

**Interfaces:**
- Produces:
  - `WriteJob` (frozen dataclass): `operation: str` (`"write"` | `"erase"`), `offset: int`, `length: int`, `data: Optional[bytes]` (`None` for erase), `source: str` (e.g. `"file /path/x.bin (sha256 ab12…)"`, `"data_hex (4 bytes)"`, `"erase to 0xFF"`).
  - `parse_job(opts: Dict[str, Any], size: int) -> WriteJob`. Raises `ValueError` with a plain sentence. Rules: `operation` defaults to `"write"`. `offset` is an int with `0 <= offset < size` (bools refused). A write needs exactly one of `file` (`~` expanded, must be an existing regular file of 1 to `size - offset` bytes, read now) or `data_hex` (parsed like `jobs._hex_bytes`, same limit). An erase takes neither, and `length` defaults to `size - offset`.
  - `WRITE_OPTIONS = {"operation": "write", "offset": 0, "file": None, "data_hex": None, "length": None, "backup": True}`, merged into each write recipe's options.
  - `prepare(job, read: Callable[[int, int], bytes], chip: str, label: str, keep_backup: bool, span: Optional[Tuple[int, int]] = None) -> Dict[str, Any]`. `span` is the range the chip really rewrites (default: the job's range). It reads the span, and saves it with `backup.save(old, "%s-%06x" % (label, span_start))` when `keep_backup` is true. It returns the public keys from Task 1, plus `span_start`, `span_length`, `source`, and `_job`, `_old`, `_sha` (the sha256 of `old`). `summary` names the chip, the operation, the byte range in hex, the source, and either the backup path or "no backup (declined)".
  - `commit(prepared, read, write_span: Callable[[int, bytes], None]) -> Dict[str, Any]`. It re-reads the span: if the sha differs, it returns `{"error": CHANGED}` with `CHANGED = "plan again: the chip's contents changed since the backup (another chip, or another write); nothing was written"`. Otherwise it builds `image` (`old`, with the job's data, or `0xFF` for an erase, over the job's range), calls `write_span(span_start, image)`, reads the span back, and returns `{"written": job.length, "span_start", "span_length", "verified": bool, "mismatches": int, "first_bad": "0x…"|None, "backup": prepared["backup"]}`. When not verified it adds `hint`: "the chip did not take the change — check its WP pin and write protection; the backup is at <path>".

**Interfaces:**
- Produces:
  - `spd.crc16(data: bytes) -> int`: CRC-16/XMODEM (poly 0x1021, init 0); `crc16(b"123456789") == 0x31C3`.
  - `spd.read_ddr4(i2c, address=0x50) -> bytes` (512 bytes). Each 256-byte page is selected with `i2c.write(0x36 + page, b"")`. The page is confirmed by reading one byte at 0x36: the read answers on page 0 and raises `NackError` on page 1. If the confirmation fails, it retries the select with `b"\x00"`, ignoring a `NackError` on that write. If it still fails, it raises `SpdError("the module did not switch SPD pages")`. It always returns to page 0. `# UNVERIFIED on hardware`.
  - `spd.read_ddr5(i2c, address=0x50) -> bytes` (1024 bytes). For pages 0–7: `i2c.write(address, bytes([0x0B, page]))` (MR11), then `read_after_write(address, b"\x80", 128)`. It ends with MR11 set back to 0.
  - `spd.decode(data: bytes) -> Dict[str, Any]` with these keys:
    - `memory_type`: byte 2, where 0x0C is DDR4 and 0x12 is DDR5; anything else is `"unknown 0x.."`.
    - `module_type`: byte 3 & 0x0F, where 1 RDIMM, 2 UDIMM, 3 SO-DIMM, 4 LRDIMM; anything else is `"type 0x.."`.
    - `manufacturer`: DDR4 bytes 320–321, DDR5 bytes 512–513. It is `"bank N, 0xXX"`, plus the name from `devices.JEDEC_MANUFACTURERS` when the bank is 1.
    - `part_number`: ASCII, stripped. DDR4 bytes 329–348, DDR5 bytes 521–550.
    - `serial`: hex. DDR4 bytes 325–328, DDR5 bytes 517–520.
    - `crc_ok`: a list of bools. DDR4 has two blocks: 0–125 checked against 126–127, and 128–253 against 254–255. DDR5 has one block: 0–509 against 510–511. Each CRC is stored little-endian.
    - `warning`: set when any CRC is bad.
  - Recipes `ddr4-spd` and `ddr5-spd` (risk none): bus i2c, default 5000, range 4500–5000 (the plank makes its own 3.3 V), pull-ups off (the plank has its own), wiring `(("5V", "VOUT"), ("GND", "GND"), ("SDA", "IO0"), ("SCL", "IO1"))`, options `{"address": 0x50}`.

    - Notes: "take the module out of the computer; seat it in the plank before power-on", "read only: writing SPD can stop a module from booting", and for DDR5 "the plank's HSA jumper goes to GND (offline mode, address 0x50)".
