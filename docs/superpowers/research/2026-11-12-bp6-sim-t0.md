# BP6 SIM report: T=0 over the HDUART terminal (research, Task 1 Step 1)

Firmware source: BusPirate5-firmware commit `e2429e0c`. Paths are under `src/`.

## 1. How a bus-syntax write is echoed

- A line such as `0xA0 0xA4 0x00 0x00 0x02` is compiled, run and then printed,
  in that order (`ui/ui_process.c`, `ui_process_syntax`: `syntax_compile`,
  `syntax_run`, `syntax_post`). Nothing is printed while the bytes go out.
- Each byte goes out through `mode/hwhduart.c`, `hwhduart_write` ->
  `pirate/hwuart_pio.c`, `hwuart_pio_write`.
- `syntax_post` prints the writes (`syntax_post.c`, `postprocess_mode_write`):
  `\r\nTX: ` once per run of writes, then each value and a space, 8 values per
  row, a new row starting `\r\n    `.
- The value format: with the default display format (`df_auto`) a write is
  printed in the format it was typed (`syntax_post.c`,
  `postprocess_format_print_number`). Hex is printed by `ui/ui_format.c`,
  `format_print_hex`: `0x` then **upper-case** digits from `ascii_hex`
  (`ui/ui_const.h`). So `0xa0` typed is echoed `0xA0`.

## 2. How received bytes are printed

- `[` sets `mode_config.async_print` (`hwhduart_open`); `]` clears it
  (`hwhduart_close`). The flag persists across command lines: a later line of
  plain writes does not change it.
- `hwhduart_periodic` prints each received byte as `printf("0x%02x ", cooked)`:
  **lower-case** hex, one space after.
- `protocol_periodic` is called only from the main loop in the
  `BP_SM_GET_INPUT` (and toolbar-focus) states (`pirate.c`), that is, after
  the prompt and its end marker `\x03` have been printed. It is never called
  during `syntax_run` or `syntax_post`.

**So the two never interleave.** The output of one write line is: echo,
`TX:` row(s), prompt, `\x03`, and only then the card's bytes. Bytes the card
sends while the line is still being run or printed wait in the PIO RX FIFO,
which is joined to 8 entries (`pirate/hwuart.pio`, `uart_rx_program_init`,
`PIO_FIFO_JOIN_RX`), and print after the prompt.

How they are told apart: the received bytes are the lower-case `0x%02x`
tokens **after the TX echo**. A digit-only byte (`0x00`, `0x20`) looks the
same in both cases, so case alone is not enough: the parser removes the
`TX:` row and its indented continuation rows first, then takes the
lower-case tokens that are left.

## 3. Listen mode and the line direction

`m hduart ... -l listen`: `hwuart_pio_init` leaves the RXTX pin as an input
and the TX state machine disabled. `hwuart_pio_write` with `cfg->listen`
disables RX, claims the buffer and pin direction (`bio_buf_output`,
`pio_sm_set_consecutive_pindirs(..., true)`), sends one byte (parity and the
second stop bit added in software), waits for the TX state machine to stall,
then releases the pin and buffer (`bio_buf_input`) and re-enables RX. So the
line is driven only for the duration of each byte, and the board never hears
its own bytes (RX is off while it sends). This is what a SIM needs: the card
can answer on the same wire straight after the last byte.

`hwhduart_read` (`r`) gives up after a 0xfff-iteration spin, far too fast for
a card, and is never used; reading is the async print only.

## 4. Decisions (send format)

- **One terminal line per command header**: five bytes, upper-case hex with
  `0x`, e.g. `0xA0 0xA4 0x00 0x00 0x02`. VERIFY with a PIN is therefore the
  single identifiable line `0xA0 0x20 0x00 0x01 0x08` (or class `0x00`),
  which Task 4 can declare as the commit's change line.
- **One line per data block** after the card's procedure byte: all remaining
  data after INS, one byte after INS XOR FF. Blocks longer than 48 bytes are
  split into lines of 48 (each line stays under 256 characters); the SIMs
  here never send more than 8 data bytes (VERIFY), 2 for SELECT.
- Async print (`[`) stays on for the whole session, from the ATR to
  `SimLink.close`, which sends `]` then `g 1`.
- After each line, the link reads the bytes that followed the prompt (in the
  reply and then by `Console.collect` in short slices) until it has what T=0
  says comes next, or until the work waiting time passes with no new byte
  (default 960 x WI(10) x 372 / f = 1.0 s at 3.5712 MHz, plus 0.5 s for the
  USB/terminal latency). Every byte is read before the next line is sent,
  because `Console.command` drains (discards) waiting input first.

## 5. Risks to check on hardware

- The 8-entry RX FIFO: a READ BINARY's INS + data + SW start right after the
  fifth header byte, while the firmware still prints the `TX:` row and the
  prompt. At 9600 baud a character takes about 1.25 ms (12 etu), so more than
  8 bytes would need about 10 ms of printing to overflow. USB CDC printing of
  ~40 characters should be far quicker, but this is the first thing to watch
  on the real board (missing bytes in the middle of a long read).
- A card's parity-error signal (pulling the line low in the guard time) is
  not handled by the PIO program; a repeated character would show as an extra
  byte. Not expected at 9600 baud on a short lead.
